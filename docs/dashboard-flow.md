# Dashboard API dependencies

Source: AWAKEN_ATLAS Postman collection supplied by the project owner. Admin requests are excluded from dashboard services.

1. Register once with `POST /auth/register`; sign in with `POST /auth/login`; verify the token with `GET /auth/me`. Only the backend role decides dashboard access. Email verification is not a frontend access gate.
   Login keeps the verified role's default dashboard. A verified FACILITATOR can also open the User workspace for their own learning account and switch back to teaching; USER/unknown/admin identities cannot open the teaching workspace. Application approval without a verified FACILITATOR role never grants teaching access. Public desktop/mobile navigation verifies `/auth/me` and shows Profile → `/dashboard/user` instead of sign-in/register links for authenticated users; cached local identity is not an authorization source.
2. USER: `/me/dashboard`, `/me/courses` → course detail → lessons/access-link → progress → certificates. Explore uses existing public catalogue and checkout pages; paid access is decided by backend enrollment/entitlements, never by frontend payment state.
3. Workshops: `/me/classes` → class details → join/recording/cancel; sessions: `/me/sessions` → booking detail → join/reschedule/cancel. Orders retain existing quote → checkout → payment-attempt → verification dependencies.
4. Application: GET current → POST draft → PATCH professional/personal/bank details with current version → multipart documents → review → POST submit with current version → GET status. Reopen uses the documented `/reopen` operation. Its eligibility and approval statuses must come from backend responses; the collection has no response examples or exhaustive application status enum. Approval alone never grants frontend FACILITATOR access; recheck `/auth/me`.
5. FACILITATOR: verify `/auth/me` → `/facilitator/dashboard`; create course from live category/language/level dependencies → curriculum sections/lessons with current courseVersion → submit. Workshops/session types/availability precede registrations and bookings. Earnings summary/sales precede payout request with a persistent intent key.
   Earnings uses only GET `/facilitator/earnings?currency=...&page=...&limit=20`, `/facilitator/earnings/summary?currency=...`, and `/facilitator/earnings/:id`. Applied currency is shared by list and summary, defaults to the collection's INR value, and is preserved in detail/back links. Empty `data: []` with `pagination.pages: 0` stays empty; summary/detail fields come from returned data. No sales-report request or fabricated earnings figure is needed for this page.
   Overview calls `GET /facilitator/dashboard?limit=5` and maps the supplied summary contract (`totalCourses`, `pendingCourses`, `totalClasses`, `upcomingClasses`, `totalStudents`, `courseEnrollments`, `sessionBookings`, and `productSales.sales/units`). Backend zeros stay zero; absent counters stay unavailable. `asOf` supplies the updated time. Finances remain separated by currency; recent sales/questions come directly from their response arrays. No `activeCourses`, combined `totalRevenue`, course list, registration list or chart series is inferred from this endpoint. Populated finance/sale/question item schemas were not supplied, so returned scalar fields are displayed without inventing records or totals.
   Announcements: paginated GET list → POST draft → GET detail → PATCH with latest version → POST publish with latest version and reason. DELETE also sends the collection's version/reason body. The dashboard exposes the supplied `ALL_MY_STUDENTS` audience and `IN_APP`/`EMAIL` channels. Draft/published status and publication time are rendered from backend responses; no sample announcement is seeded and no live messages were sent during validation.
6. Collection has no wishlist API or standalone community API. Do not invent either. Community uses course Q&A. Wishlist displays an honest availability state.
7. All protected proxy routes match an endpoint/method allowlist extracted from this collection; administrator and webhook routes are excluded. Bearer tokens remain in HttpOnly cookies; mutations require same-origin CSRF validation. Ownership, status transitions and final permission decisions remain backend-enforced.

## Verification limits

The collection contains request contracts but no saved response examples. Real role credentials and actual application review results are needed to verify approval activation, payment providers, file access and every production transition. Never seed fake dashboard numbers or create a second facilitator account.

The documented lesson-create body contains `courseVersion`, `sectionId`, `title`, and `contentType`; the lesson-patch example contains `courseVersion` and `sectionId`. No media-to-lesson binding field is documented. Media uploads and authorized file access are implemented, but assigning a newly uploaded file to a lesson requires an explicit backend request contract. Do not guess a `mediaId`, `videoId`, or attachment endpoint.

Existing `.env` values are preserved. No local account database, Postman demo fixtures, admin calls or seeded dashboard values are used. Test fixtures are isolated within the contract test runner and are never rendered by the application.

## Validation completed

- Production build: `next build --webpack` passed; 57 static pages generated, with dynamic dashboard routes compiled.
- Scoped ESLint checks passed for the dashboard, authentication, protected proxy and changed account integrations.
- `node --test tests/dashboard-contracts.test.mjs`: 21 passing isolated contract/security tests covering collection matching, earnings queries and empty pagination, role-safe workspace switching, exact facilitator overview mapping and zero/absent values, role checks, announcement lifecycle payloads and pagination, CSRF, version bodies, multipart uploads, range streaming, registration and session refresh.
- Read-only requests against the configured backend returned successful health, public courses and public website responses. No live account creation, payment, payout, contact submission or administrator operation was performed.
- Authenticated browser flows, approval activation and payment completion remain unverified because test account credentials were not available. These checks do not establish that every backend response shape or production transition works.
